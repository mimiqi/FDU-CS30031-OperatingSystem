# Trace 技术指导

## 1 本模块的完成目标

本次交付以指导和参考代码为限，不要求实际运行。下面的编译、测试和报告步骤供以后在 VMware Ubuntu 24 中实践时使用；Attack 当前暂时跳过。

实现 `trace(int mask)` 系统调用，让当前进程及其后续 `fork()` 出来的子进程，可以选择性地打印系统调用的执行结果。

例如在 xv6 中运行：

```sh
trace 32 grep hello README
```

`32 = 1 << 5`，而此分支的 `SYS_read` 为 5，因此只跟踪 `read`。每行需要输出进程 PID、调用名称和返回值。示意输出如下，数字以实际运行结果为准：

```text
3: syscall read -> 1023
3: syscall read -> 0
```

本模块通过的标准是：指定的调用能被跟踪、没有选择的调用不输出、普通程序不受影响、子进程继承跟踪设置。

## 5 理解 Trace 会经过哪些地方

普通系统调用的大致路径为：

```text
用户程序调用函数
    user/user.h 中的声明
    user/usys.pl 生成的汇编入口
    a7 放入系统调用编号，执行 ecall
    usertrap() 处理用户态陷阱
    syscall() 读取 a7 并查询 syscalls[]
    sys_xxx() 执行实际工作
    返回值写入 trapframe->a0
    返回用户态
```

`trace` 用户程序已经由实验仓库提供。它先调用 `trace(mask)`，随后通过 `exec()` 执行你指定的程序，例如 `grep`。`exec()` 会替换程序内容，但仍使用同一个进程，因此保存在 `struct proc` 中的 mask 应当继续有效。

`fork()` 会创建新的进程结构，必须额外复制 mask。把 mask 写成全局变量会导致其他进程也受影响，因此必须保存在每个进程自己的 `struct proc` 中。

## 6 实践阶段一 接通用户态入口

本阶段修改四个位置。可以用 Ubuntu 中习惯的编辑器；例如 `nano user/user.h`，保存时按 `Ctrl+O`、回车，退出按 `Ctrl+X`。

### 6.1 Makefile

找到已有的 `ifeq ($(LAB),syscall)` 区块，在它的 `UPROGS` 中加入 `_trace`：

```make
ifeq ($(LAB),syscall)
UPROGS += \
	$U/_trace\
	$U/_attack\
	$U/_attacktest\
	$U/_secret
endif
```

保留该区块已有的项目，不要把整个 `UPROGS` 列表替换掉。注意续行的反斜杠以及 Makefile 原有的缩进。

### 6.2 user/user.h

在系统调用声明区域追加：

```c
int trace(int);
```

### 6.3 user/usys.pl

在其他 `entry(...)` 项后追加：

```perl
entry("trace");
```

此文件会自动生成 `user/usys.S`。直接编辑生成出来的 `usys.S`，下次构建时会被覆盖。

### 6.4 kernel/syscall.h

本学习包对应的官方基线最后一个编号是 `SYS_close 21`，因此追加：

```c
#define SYS_trace 22
```

如果你的老师修改过编号，先检查空闲编号。`SYS_trace` 不能与已有系统调用重复，且必须和后面的函数表保持一致。

### 本阶段检查

在 Ubuntu 终端执行：

```sh
make qemu
```

此时 `trace` 的用户程序应能编译。进入 xv6 后运行 `trace 32 grep hello README`，仍可能看到未知系统调用或 `trace failed`，因为下一阶段才实现内核部分。退出 QEMU 后继续。

## 7 实践阶段二 保存每个进程的 mask

### 7.1 kernel/proc.h

在 `struct proc` 末尾、最终的 `};` 之前加入：

```c
uint trace_mask;
```

每个 `struct proc` 都有独立字段。这里用无符号整数保存位掩码。

### 7.2 kernel/proc.c 的 allocproc

找到 `found:` 后的进程初始化位置：

```c
found:
  p->pid = allocpid();
  p->state = USED;
  p->trace_mask = 0;
```

这个初始化很重要。进程退出后，内核会重新使用旧的进程槽位；不清零可能让后来的普通进程继承无关的跟踪设置。

同时，在 `freeproc()` 中与 `p->xstate = 0` 等清理语句放在一起，加入：

```c
p->trace_mask = 0;
```

### 7.3 kernel/sysproc.c

在文件已有 `#include` 之后加入一个系统调用处理函数：

```c
uint64
sys_trace(void)
{
  int mask;

  argint(0, &mask);
  myproc()->trace_mask = (uint)mask;
  return 0;
}
```

这里 `argint(0, &mask)` 读取第一个参数，`myproc()` 找到当前进程。**2024 版的 `argint()` 返回 `void`**，不能照抄旧教程写成 `if (argint(...) < 0)`。

## 8 实践阶段三 在分发器打印结果

### 8.1 注册处理函数

在 `kernel/syscall.c` 的其他 `extern uint64 sys_xxx(void);` 后追加：

```c
extern uint64 sys_trace(void);
```

在 `syscalls[]` 数组中追加一项：

```c
[SYS_trace] sys_trace,
```

### 8.2 按编号建立名称表

在 `syscalls[]` 后面、`syscall()` 函数前面加入：

```c
static const char *syscall_names[] = {
  [SYS_fork] = "fork",
  [SYS_exit] = "exit",
  [SYS_wait] = "wait",
  [SYS_pipe] = "pipe",
  [SYS_read] = "read",
  [SYS_kill] = "kill",
  [SYS_exec] = "exec",
  [SYS_fstat] = "fstat",
  [SYS_chdir] = "chdir",
  [SYS_dup] = "dup",
  [SYS_getpid] = "getpid",
  [SYS_sbrk] = "sbrk",
  [SYS_sleep] = "sleep",
  [SYS_uptime] = "uptime",
  [SYS_open] = "open",
  [SYS_write] = "write",
  [SYS_mknod] = "mknod",
  [SYS_unlink] = "unlink",
  [SYS_link] = "link",
  [SYS_mkdir] = "mkdir",
  [SYS_close] = "close",
  [SYS_trace] = "trace",
};
```

`[SYS_read] = "read"` 表示把字符串放在系统调用编号对应的下标中。这样不用手动猜测数组中第几项是什么。

### 8.3 在系统调用返回后打印

找到 `syscall()` 中原来的语句：

```c
p->trapframe->a0 = syscalls[num]();
```

保留这条语句，在其后加入：

```c
if(num < 32 && (p->trace_mask & (1U << num)) != 0){
  printf("%d: syscall %s -> %ld\n",
         p->pid, syscall_names[num], (long)p->trapframe->a0);
}
```

这段必须放在原有的合法调用编号判断之内。数组访问之前仍要保留 `num > 0`、`num < NELEM(syscalls)` 和函数指针非空的检查。

几个关键点：

- 用 `&` 检查某一位，而不是用 `&&`。`1U << num` 只把编号为 `num` 的那一位置 1。
- 本参考方案用 32 位 mask，因此先判断 `num < 32`，避免移位超出位宽。
- 在处理函数返回后输出，才能取得真正的返回值，也能让 `trace()` 本身按新设置的 mask 被跟踪。
- `%ld` 和 `(long)` 对应此 xv6 的 LP64 数据模型，能显示完整的有符号返回值。
- 像 `exit()` 这样的系统调用不会回到分发器的返回位置，因此不必期待它产生一条正常的返回日志。

## 9 实践阶段四 让子进程继承

在 `kernel/proc.c` 的 `fork()` 中找到：

```c
*(np->trapframe) = *(p->trapframe);
```

在它后面加入：

```c
np->trace_mask = p->trace_mask;
```

`p` 是父进程，`np` 是新建子进程。复制应在子进程变成 `RUNNABLE` 之前完成。`exec()` 不需要清除 Trace mask，否则 `trace` 执行 `grep` 后跟踪设置会消失。

## 10 编译和逐项验收

在 Ubuntu 终端执行：

```sh
make clean
make CPUS=1 qemu
```

先用一个 CPU，输出更容易阅读。进入 xv6 shell 后，逐条执行以下命令，每条执行完再输入下一条。

### 10.1 只跟踪 read

```sh
trace 32 grep hello README
```

期望跟踪行只出现 `read`，最后一次读到文件末尾时返回 0。PID、读取次数和每次读到的字节数以你自己的运行结果为准。

### 10.2 跟踪全部已定义的调用

```sh
trace 2147483647 grep hello README
```

期望出现 `trace`、`exec`、`open`、`read`、`close` 等调用的记录。返回值来自各自的实现，例如 `exec` 的成功返回值不应简单假定为 0。

### 10.3 普通程序不受影响

```sh
grep hello README
```

期望没有 `PID: syscall ...` 格式的跟踪行。普通 `grep` 是否输出文本取决于 README 的内容。

### 10.4 子进程继承

```sh
trace 2 usertests forkforkfork
```

`2 = 1 << SYS_fork`，期望多个不同 PID 都能输出 `fork` 调用记录。测试可能故意制造进程耗尽，出现 `fork -> -1` 不等于你的 Trace 实现错误；结合测试末尾的结果判断。

### 10.5 零 mask 关闭跟踪

```sh
trace 0 grep hello README
```

期望没有跟踪行。这是方便理解 mask 的额外检查。

### 10.6 运行 Trace 自动测试

退出 QEMU，回到 Ubuntu 终端：

```sh
make GRADEFLAGS=trace grade
```

该命令只选择名称包含 `trace` 的测试。本基线有六项 Trace 测试，全部应为 `OK`。也可以直接运行：

```sh
python3 grade-lab-syscall trace
```

不要同时保持另一个 QEMU 占用同一份 `fs.img`。

**当前只完成 Trace 时，整套 `make grade` 不一定全通过。** `attack` 按本次要求暂时跳过，此外官方评分脚本还会检查 `answers-syscall.txt` 和 `time.txt`。课件没有把 MIT 的 GDB 问答列为独立实验，本课程是否需要补充这些文件应以老师要求为准；不要为消除失败项而编造运行结果或耗时。

## 11 常见错误如何定位

### 编译器说 trace 没声明

检查 `user/user.h` 中的原型是否存在，是否保存了正确的文件，当前仓库是否为 2024 实验仓库。

### 链接器说 undefined reference to trace

检查 `user/usys.pl` 是否追加 `entry("trace");`，再执行 `make clean` 后重编。不要仅修改 `usys.S`。

### xv6 提示 unknown sys call 22

检查 `kernel/syscall.c` 中的 `sys_trace` 声明及 `syscalls[]` 注册是否齐全，编号是否一致。

### 提示 void value not ignored

通常是把此版本的 `argint()` 当成返回整数的旧接口。改为单独调用 `argint(0, &mask);`。

### 全部普通程序都被跟踪

检查 mask 是否误写成全局变量，或 `allocproc()` 是否没有清零。普通 shell 的 mask 应保持为零。

### 父进程能输出 子进程没有输出

检查 `fork()` 是否把 mask 复制给 `np`，以及复制是否在子进程成为 `RUNNABLE` 之前完成。

### trace 本身被跟踪 但 grep 没有

检查是否在 `exec()` 中误清零了 Trace mask，或在读取参数和测试 mask 时使用了错误的位运算。

### 输出调用名错位

检查名称数组是否用 `[SYS_xxx]` 指定下标，是否缺少系统调用对应名称。

### 在 Ubuntu 输入 trace 却找不到命令

实验的 `trace` 是 xv6 用户程序，需要先运行 `make qemu`，再到 xv6 的 `$` 提示符下输入。

## 12 报告应当说明什么

完成测试后，在 [实践记录](实践记录.md) 中填写实际输出与截图路径，随后用于编写 System calls 报告的 Trace 部分。

应能够用自己的话解释：

1. 一个新系统调用为什么同时要修改用户态入口和内核分发表。
2. mask 的某一位如何对应系统调用编号。
3. mask 为什么放在 `struct proc` 中。
4. 为什么在系统调用执行后输出返回值。
5. `fork()` 和 `exec()` 对跟踪设置分别有什么影响。
6. 未被跟踪的普通程序为什么不受影响。

本参考包尚未在你的虚拟机中运行。报告中的结果应来自 VMware Ubuntu 24 的实际测试。
