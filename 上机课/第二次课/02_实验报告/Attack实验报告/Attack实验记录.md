## 一、实验目的

利用教学分支故意保留的页面清理缺陷，理解物理页回收、再次分配与进程间数据隔离的关系。程序只读取重新分配给自己的用户内存，并按测试程序的约定返回残留的 8 字节 secret。


## 二、内存隔离机制与漏洞原因

### 2.1 页表隔离与数据残留

正常情况下，每个进程通过自己的页表访问用户内存，不能直接读取另一个仍然拥有页面的进程的任意地址。

本实验中的问题发生在页面更换使用者之后：`secret` 退出并释放物理页，分配器随后可能把这些物理页交给 `attack`。新进程虽然是通过自己的合法虚拟地址访问页面，但页面内容没有被清理，因此仍可能读到前一个进程留下的数据。

这说明，页表权限正确并不自动保证页面重新分配后的数据保密性。

### 2.2 实验分支中的页面清理缺陷

本实验使用 `LAB_SYSCALL` 编译条件。原版教学代码通过 `#ifndef LAB_SYSCALL` 跳过以下操作：

- `kernel/vm.c` 的 `uvmalloc()` 中，对新用户页面执行的清零。
- `kernel/kalloc.c` 的 `kfree()` 中，对释放页面执行的垃圾数据填充。
- `kernel/kalloc.c` 的 `kalloc()` 中，对新分配页面执行的垃圾数据填充。

其中后两项原本是调试用的垃圾填充，不应与清零混为一谈。这三处均不再覆盖页面内容时，旧数据便可能在重新分配后保留下来。完成本模块不需要为 Attack 修改这些内核文件，已有 Trace 实现也应保留。

### 2.3 为什么页内偏移 32 处的数据可能保留

在该版本中，空闲页本身被用来保存空闲链表节点。`kfree()` 将 `struct run` 的 `next` 指针写到页首，在 RV64 环境中占用前 8 字节。

因此，即使整页未被清理，页首内容仍可能被链表指针覆盖。

## 三、测试程序如何判断成功

依据本实验的原版 `user/attacktest.c`，测试过程为：

1. 使用 `uptime()` 初始化随机数状态，生成 7 个字符和一个结尾零字节，共 8 字节的 secret。
2. 创建子进程并执行 `secret`，把这份 secret 作为参数传入。
3. 等待 `secret` 退出，使其页面进入回收与复用过程。
4. 创建管道并启动 `attack`，将 `attack` 的文件描述符 2 接到管道写端。
5. 从管道读取结果，与原 secret 进行字符串比较；一致时输出 `OK: secret is ...`。

原版 `secret.c` 申请 32 页堆空间，在该区域下标为 9 的页面，即第 10 页的页内偏移 32 处保存 secret。

这里的页号属于 `secret` 自己的地址空间。`attack` 再次申请页面时，中间已经发生页面释放、管道分配、`fork` 和 `exec` 等操作，因此不能将两个进程的新分配区域页号直接等同起来。

## 四、本次实际代码

以下为用户本次提供的 `user/attack.c`

```c
#include "kernel/types.h"
#include "kernel/fcntl.h"
#include "user/user.h"
#include "kernel/riscv.h"
int
main(int argc, char *argv[])
{
  if (argc != 1) {
    printf("Usage: attack\n");
    exit(1);
  }
  char *end = sbrk(PGSIZE*32);
  end = end + 16 * PGSIZE;
  printf("secret: %s\n", end+32);
  write(2, end+32, 8);
  exit(0);
}
```

### 4.1 申请与定位

`sbrk(PGSIZE*32)` 请求扩展堆空间，成功时返回旧堆顶，即新区域的起始地址。在本实验中 `PGSIZE = 4096`，因此请求大小为 131072 字节，即 128 KiB。

`end = end + 16 * PGSIZE` 将指针移到新区域下标为 16 的页面，**即按自然顺序计数的第 17 页**。随后 `end+32` 指向该页内偏移 32 处，对应新区域起点加上 `16 × 4096 + 32 = 65568` 字节。

在申请成功的前提下，从该地址读取的 8 字节位于这次申请的 32 页范围内。本次测试结果表明，该位置的数据与测试程序生成的 secret 一致。

### 4.2 调试显示与测试输出

`printf("secret: %s\n", end+32)` 将读取到的字符串显示到标准输出，用于观察结果。

`write(2, end+32, 8)` 将这 8 字节写到文件描述符 2。测试程序已将 fd 2 重定向到管道，因此这一行才是向 `attacktest` 返回数据的实际接口；仅看到调试显示并不能独立证明测试成功。

本次可见字符串为 `ec/edfc`，包含 7 个字符；按测试程序生成格式，第 8 字节是字符串结束符。代码不是将这份字符串写死，而是从所定位的内存中读取并发送。

## 六、实现特点与验证边界

本次代码保留了实验思路的最小形式，同时存在以下适用范围限制：

1. 固定使用页下标 16，依赖当前程序布局与页面分配顺序，尚无跨构建或多次重新启动的验证记录。
2. 未检查 `sbrk()` 是否返回失败值；本次成功结果不代表已覆盖内存不足的路径。
3. 调试用 `%s` 依赖该位置存在字符串结束符；若固定位置失效，不能保证其读取长度。
4. 未检查 `write()` 的返回值，尚未覆盖写入失败或短写的处理路径。

以上仅说明现有实现的边界，不代表已经修改用户提供的代码，也不否定本次 `attacktest` 的实际通过结果。
