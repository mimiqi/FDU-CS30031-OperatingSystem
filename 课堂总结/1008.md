线程库与多线程编程接口
上节课已经建立了线程的基本概念：经典进程模型包含两个组成部分，一是作为资源拥有者（resource ownership）的进程，它持有地址空间、打开的文件和分配的硬件资源；二是作为调度与分派实体的进程，它可以被分配处理器来执行代码。现代操作系统将这两者分离，进程主要负责资源管理，而线程成为独立的调度与分派单位。在同一个地址空间内，可以同时存在多个可执行的线程，它们共享进程的资源池。

线程拥有自身独立的执行上下文，包括线程栈（stack）、线程描述符（线程控制块）、执行模式（execution mode）和执行状态（运行、就绪或阻塞）。而资源相关的信息则归属于进程级别。这种设计使得同一进程内的多个线程之间通信和同步非常方便，因为它们天然共享地址空间。同时，线程的创建成本远低于创建进程，因此被称为轻量级调度分派实体。

线程库（thread library）为程序员提供了创建和管理线程的 API 接口。其实现主要有两种类型：一种是完全在用户空间提供的用户级线程库，此时操作系统并不感知线程的存在；另一种是由操作系统直接支持的内核级线程库。实际使用中，常见的线程库包括 POSIX 标准的扩展 Pthreads、Windows 系统的 Win32 线程 API，以及 Java 线程。Java 线程的底层实现取决于其运行的主机平台：如果 Java 运行环境安装在 Windows 系统上，它通常调用 Win32 API；如果安装在类 Unix 系统上，则可能使用 Pthreads。

以 Pthreads 为例，一个典型的多线程程序结构是：主函数启动时即存在一个主线程，主线程调用 pthread_create 创建子线程，子线程执行指定的函数（例如 runner），主线程随后调用等待函数阻塞自身，直到子线程运行结束才继续执行。这种模式中，主线程和子线程通过全局变量进行通信——子线程将计算结果写入全局变量，主线程等待后读取并输出。两个线程之间存在一个简单的同步约束关系，实际上它们是以串行方式执行的，而不是并发执行，因此在此示例中不会发生共享变量访问冲突。

Win32 线程库的功能与此类似，只是 API 名称不同，使用 CreateThread 创建线程。不同的线程库虽然在函数命名上有所差异，但基本功能是一致的：创建线程、设置同步等待关系和通过全局变量进行线程间通信。

多线程环境中的若干设计问题
fork 系统调用与写时复制
fork 是进程派生系统调用。在 Linux 等系统中，常见的使用模式是 fork 后紧跟 exec：父进程先派生出一个拥有相同地址空间的子进程，子进程随后调用 exec 载入并执行另一个程序。问题在于，如果 fork 时要完全复制一份与父进程完全相同的地址空间，而子进程随后很可能立即执行 exec 完全替换掉这份地址空间，那么之前的完整复制就是浪费。

为此，Linux 引入了写时复制（Copy-On-Write, COW）机制。在执行 fork 时，操作系统并不真正复制父进程的物理内存页面。父进程和子进程的页表项都指向相同的物理内存页，两者共享同一份内容。如果双方只对这些页面进行读操作，共享完全不会产生问题，因为在两个进程眼中内容始终一致。一旦某个进程试图对某一页面进行写操作，操作系统会通过硬件机制检测到这一写行为——该页面被标记为不可写，写操作会触发异常——此时系统才为该页面复制一份副本，让写入方对副本进行修改，而另一方仍然看到原始内容。COW 机制极大地提升了 fork 的性能，因为它避免了无效复制，只在真正需要的时候才付出复制代价。

多线程环境中的 fork 还面临另一个设计问题：派生新进程时，是复制父进程的所有线程，还是仅复制调用 fork 的那个线程？这个选择取决于应用场景。如果 fork 之后立即执行 exec，那么复制所有线程就不必要；但如果在 fork 之后并不执行 exec，则可能需要保留所有线程。这是操作系统设计者需要权衡的决策。

线程撤销
线程撤销（thread cancellation）指的是在线程自然结束之前终止它。典型应用场景包括：在数据库中并行搜索时，一旦某一个线程找到结果，其他仍在搜索的线程就需要被撤销；或者在交互式环境中，用户点击浏览器上的停止按钮，多个负责下载不同图片的线程就需要被终止。

线程撤销的难点在于：被撤销的线程可能正在更新与其他线程共享的数据。如果在更新过程中途将其终止，会导致共享数据结构不一致或数据丢失。同时，撤销前如果该线程已经分配了某些资源，撤销时可能来不及释放，造成资源泄漏。

解决这一问题有两种基本方式。异步撤销（asynchronous cancellation）是指一个线程可以立即终止目标线程，无论目标线程当前处于什么状态，这种方式简单粗暴但有上述风险。延迟撤销（deferred cancellation）则是向目标线程发出撤销请求，目标线程在运行过程中周期性地检查自己是否应该被终止。当目标线程处于重要临界区域（例如正在更新共享数据）时，它不去检查撤销请求；只有离开这些敏感区域后，才检查并有序地终止自己。这样可以保证线程在合适的时机释放资源、完成数据更新后再退出。Pthreads 中通过 pthread_cancel 发起撤销请求，实际是否撤销取决于目标线程的设置模式，可以配置为禁用、延迟或异步。

多线程环境中的信号处理
信号（signal）是 Unix 系统中一种单向的异步通知机制。Shell、窗口管理器、内核等都可以向进程发送信号，进程通过信号处理程序（signal handler）来响应。例如用户按下 Ctrl+C 时，系统会向当前进程发送相应的信号，默认处理方式是终止该进程。常见的信号类型包括同步信号和异步信号：同步信号源于进程内部无效操作引发的异常或错误，异步信号则来自进程正常运行之外的事件，如定时器到期或用户输入。

在传统单线程进程模型中，信号发送给进程。但在多线程环境中，一个进程包含多个线程，信号应当发送给谁就成为一个设计问题。可选的策略包括：将信号发送给信号所针对的那个线程；发送给进程中的所有线程；发送给进程中某些特定的线程；或者指定一个专门的线程来接收进程的所有信号。具体采用哪种策略取决于所产生信号的类型。

线程池
线程池（thread pool）的基本思想是：在进程启动时预先创建若干个线程，将它们放入一个资源池中等待工作。以服务器程序为例，当服务器启动时就创建一定数量的线程，这些线程在线程池中等待即将到来的请求。当服务器接收到一个请求时，就唤醒池中的一个线程，将请求交给它处理；该线程完成服务后，不会退出，而是回到线程池中继续等待下一个请求。

线程池有两个主要优点。第一，用已有线程服务新请求比临时创建一个线程要快得多，避免了线程创建的系统开销。第二，线程池限制了系统中线程的数量上限。如果系统无法支持大量并发线程，线程池可以控制负载——例如只保留10个线程，第11个请求到来时不会被分配新线程，而是等待已有线程空闲出来。这样可以防止系统因线程数量过多而过载，代价是部分请求的响应时间会变长。

进程核心概念回顾
在进入并发性主题之前，课程对进程概念进行了系统回顾。进程是一个运行中的程序，它是动态的执行实体，而程序是静态的代码和数据。可以用烹饪来类比：菜谱相当于程序，而按照菜谱做菜的过程相当于进程。

进程在生命周期中经历创建、执行、终止等阶段，其核心状态包括：就绪态（ready）、运行态（running） 和 阻塞态（blocked），此外还有两个辅助态——就绪挂起态和阻塞挂起态。挂起态意味着进程被换出到外存，释放了主存资源；而阻塞态关注的是 CPU 资源的等待。状态之间的转换条件需要重点掌握。

操作系统为了管理进程，为每个进程维护一个进程控制块（PCB, Process Control Block），也称为进程描述符。每个进程唯一对应一个 PCB，包含进程标识符（PID）、处理器状态信息（寄存器、程序计数器等）和进程控制信息（调度参数、资源清单等）。所有进程的 PCB 集中构成进程表（process table），以 PID 为索引，操作系统可以通过 PID 快速定位到对应的 PCB。

进程控制的一个核心概念是模式切换（mode switch）与上下文切换（context switch）的区别。模式切换是指 CPU 从用户态切换到内核态，它发生在三种且仅有三种情况下：第一，硬件中断（异步中断，独立于当前运行进程）；第二，异常（当前进程内部产生的同步事件，如缺页、除零、执行特权指令等）；第三，系统调用（当前进程主动请求操作系统服务）。模式切换不一定引发上下文切换，但上下文切换必须发生在内核态，因此模式切换是上下文切换的前提。进程上下文切换的代价比线程上下文切换更高，因为前者涉及完整的地址空间切换。

并发性与进程交互
从本节课开始正式进入并发性：互斥与同步这一核心章节。在计算机系统中存在三种管理多进程或多线程的场景：单处理机系统中的多道程序设计（multiprogramming）、多处理机系统中对多个进程的管理（如对称多处理 SMP，多个 CPU 共享同一内存）、以及分布式系统中跨多台计算机的进程管理。无论哪种场景，并发性都是操作系统设计的核心问题。

进程从交互角度可分为两类。独立进程（independent processes）是指不能影响其他进程、也不受其他进程影响的进程。如果一个进程不与其他任何进程共享数据，它的执行结果不依赖于其他进程，那么它就是独立进程。独立进程无需同步或通信，例如独立运行的计算器程序。

合作进程（cooperating processes）则是能够影响或受其他进程影响的进程，它们共享数据或需要彼此协调。需要合作进程的四个原因是：

信息共享：多个进程可能需要访问同一信息片段，例如多个进程同时读写一块数据区，后面讨论的生产者-消费者问题和读者-写者问题都是典型例子。计算加速：在多处理机系统上，将大型矩阵乘法等任务分块，每个线程负责计算其中一块，利用并行计算能力加速处理。模块化：将复杂应用程序分割为多个进程或线程，每个并发实体充当一个功能模块。便捷性：例如在 Shell 中通过管道将多个命令连接起来，前一个命令的输出成为后一个命令的输入，它们共同完成同一项工作。

竞态条件、临界区与互斥
竞态条件
竞态条件（race condition）是指两个或多个进程在读写某些共享数据时，最终结果依赖于它们具体的执行顺序的情况。老师指出，race condition 翻译为“竞争条件”并不精确，更准确的理解是“竞态”，因为这里的 condition 实际指的是一种场景或情形（situation），而不是逻辑条件。

竞态条件的关键特征包括：对共享资源的并发访问；至少有一个访问是写操作；结果是非确定的，依赖于具体时序。最经典的例子是计数器递增操作。高级语言中看似一条语句的 count = count + 1，在机器指令级别实际包含三条指令：读取 count 的当前值、将读到的值加一、将结果写回。如果两个线程 A 和 B 并发执行这个递增操作，可能出现如下时序：线程 A 读取 count 得到0，线程 B 也读取 count 得到0，线程 A 计算1并写回，线程 B 也计算1并写回。最终 count 的值为1而不是2，两次递增操作丢失了一次。

为什么竞态条件值得高度关注？首先，这类错误是非确定性的——它们不总是复现。传统顺序程序中的错误每次运行都会出现，但并发程序中的竞态错误可能经过数千次测试都不出现，某一次在高负载下才突然爆发，这给调试带来极大困难。其次，竞态条件会导致数据损坏和更新丢失，例如计数错误、余额错误、内部状态不一致。第三，它可能引发安全漏洞，如 TOCTOU（time-of-check to time-of-use）攻击、权限提升和数据泄露。最后，它可能导致系统崩溃或死锁，因为不一致的内部状态可能使整个系统失效。

另一个简单例子是共享变量回显。两个进程共享全局变量 chin 和 chout。进程 P1 先执行 chin = getchar()，将用户的第一个输入字符存入共享变量；随后发生进程切换，进程 P2 执行 chin = getchar()，将用户的第二个输入字符覆盖到同一变量中。当 P1 恢复执行时，它读取的 chin 已经变成了第二个字符，导致第一个输入丢失。这个问题的根源在于：在单处理机系统中，中断可以发生在进程执行的任何位置，随时可能触发进程切换；在多处理机系统中，两个进程本身就并行执行，步调天然不确定。解决方案是对共享资源提供受控访问，特别是在涉及写操作时。

更复杂的例子是链表插入操作。两个并发进程 S 和 T 分别向链表插入数值8和18，两者都使用局部指针变量 s 和 t，初始时都指向链表头节点的后继。在顺序执行时，结果正确：8和18都被插入。但在并发执行中，如果进程 S 在完成了部分指针赋值后发生切换，进程 T 完整地执行了插入操作，随后 S 恢复执行并继续完成自己的指针操作，就会覆盖 T 的插入结果，导致18丢失。对于二叉搜索树、B树、B+树等更复杂的数据结构，并发访问引发的问题会更加严重。

临界区与互斥
临界区（critical section）是访问共享资源的代码段。当临界区正在被一个进程执行时，其他进程不能进入该代码段。互斥（mutual exclusion）就是确保当一个进程正在使用共享变量或文件时，其他进程被排斥在相同操作之外。

解决临界区问题需要满足四个要求：第一，互斥——同一时刻只能有一个进程进入临界区；第二，空闲让进（progress）——当没有进程在临界区内时，希望进入的进程不能被无故延迟，应当能够立即进入；第三，有限等待（bounded waiting）——一个进程在请求进入临界区之后，在获准之前，其他进程进入临界区的次数应有上限，即该进程的等待是有限的，不应发生饥饿；第四，让权等待——一个进程如果暂时无法进入临界区，应当主动释放 CPU，进入阻塞态等待，而不是在 CPU 上忙等消耗处理器周期。

死锁、活锁与饥饿
死锁（deadlock）是指一组进程中的每个进程都在等待该组中另一个进程才能产生的事件，导致所有进程都无法推进。十字路口的例子可以直观说明：四辆车同时到达交叉路口，分别占据一个方向的车道，每辆车都在等待另一辆车先通过，但由于谁也不退让，所有车辆都永远无法前进。死锁的特征是进程处于静态的等待状态，无法改变自己的状态。

活锁（live lock）与死锁不同：进程在不断改变自己的状态，但这些改变没有实际价值，谁也无法取得进展。十字路口场景的变体是：四面来车发现拥堵后，大家都选择倒车让行，但随后又同时向前，造成状态不断循环变化而无法真正通过。活锁中的进程可以改变状态，但始终在无效循环中空转。

饥饿（starvation）指的是一个进程请求资源但永远得不到满足。它通常与调度机制的不公平有关。典型例子是：在无交通信号灯的斑马线处，如果行人人流源源不断，汽车可能永远无法通过，因为没有排队机制来保证车辆获得通行机会。类似地，在操作系统资源分配中，如果没有公平的排队或调度策略，某些低优先级进程可能长期得不到资源分配。死锁、活锁和饥饿是互斥与同步机制设计中必须关注的三种异常现象。

进程交互的三种类型
根据进程之间对彼此存在的感知程度，可以将进程交互划分为三种类型。

资源竞争关系（competition）：进程之间完全感知不到彼此的存在。对应的是独立进程的情形。多个独立进程在系统中竞争 CPU、内存、硬件设备等资源。这类进程之间没有信息交换。对于这种关系，控制问题的核心在于互斥——某些资源一次只能被一个进程使用。值得注意的是，CPU 这类资源的使用并不会改变资源本身的状态：一个进程使用 CPU 时其处理器状态保存在自己的 PCB 中，切换时保存上下文，恢复时重新载入，不影响其他进程。而打印机这类资源虽然使用后状态可能变化，但关键仍是互斥访问。

通过共享进行合作（cooperation by sharing）：进程间接感知彼此的存在，因为它们共享一块内存区域或某个全局变量。其他进程可以修改共享数据，所以能感知到“有其他进程在活动”，但不知道具体是谁。此时控制机制必须确保共享数据的完整性。写操作必须互斥。一个典型的完整性破坏例子是：两个共享变量 a 和 b 维护不变式 a = b，初始值为 a=1, b=1。进程 P1 执行 a = a + 1; b = b + 1;，进程 P2 执行 b = 2 * b; a = 2 * a;。单独执行任何一个进程都不会破坏不变式，但并发执行时，如果 P1 执行完 a = a + 1 后发生切换（此时 a=2, b=1），P2 执行 b = 2 * b 得到 b=2，再执行 a = 2 * a 得到 a=4，切换回 P1 执行 b = b + 1 得到 b=3。最终 a=4, b=3，不变式 a=b 被破坏。

通过通信进行合作（cooperation by communication）：进程直接感知彼此的存在，通过消息传递（message passing）进行协调。此时互斥不是核心控制要求，因为进程不共享变量。但是，消息传递也可能引发死锁——每个进程都在等待来自其他进程的消息；也可能引发饥饿——两个进程持续互相发送消息，而第三个进程一直在等待却无人响应。

临界资源与互斥的抽象模型
临界资源是一次只能被一个进程访问的资源，也称为不可共享资源（nonsharable resource），例如打印机、某些变量、数据表格和队列。可共享资源是可以同时被多个进程访问的资源，也称为非临界资源，例如只读数据区和可重入程序代码。需要注意的是，如果一个共享变量存在写操作，那么写操作之间必须互斥；如果所有访问都是只读的，则可以共享。

用抽象代码表示互斥机制时，一个完整的互斥问题求解包括三个组成部分：全局变量的定义与初始化、主函数、以及每个并发进程的定义。主函数中通常使用 parbegin(P1, P2, ..., Pn) 来表示并发启动多个进程：主程序暂停执行，初始化各进程的并发执行，当所有进程终止后恢复主程序。每个并发进程的典型结构是循环执行，在进入临界区之前调用 entercritical(i)，退出临界区时调用 exitcritical(i)。这两个函数就是实现互斥的机制：entercritical 保证当已有进程在临界区内时，其他进程被阻塞在该函数处等待；exitcritical 则在退出时允许一个等待中的进程进入。

老师特别提醒：在考试中求解任何互斥或同步问题时，全局变量的定义与初始化是最容易被遗漏的部分，漏写会被扣分。

互斥的软件解决方案：Dekker 算法
软件方法实现互斥的基本假设是：在内存访问级别存在硬件保障，即对主存同一位置的并发访问由内存仲裁器（memory arbiter）进行串行化。在此基本互斥前提之上，软件方法尝试通过对共享标志变量的操作来实现临界区的互斥。典型的软件方法包括 Dekker 算法 和 Peterson 算法。课程详细分析了 Dekker 算法的逐步设计过程，以展示互斥问题中的典型陷阱。

第一次尝试：严格轮换
最简单的方法是用一个共享变量 turn 来指示当前轮到哪个进程进入临界区。turn = 0 表示进程 P0 有权进入，turn = 1 表示 P1 有权进入。进程 P0 的代码为：while (turn != 0); （忙等），然后进入临界区，退出时将 turn = 1。P1 对称执行。

这一方案可以保证互斥，但存在严重缺陷。第一，存在忙等（busy waiting）——进程占着 CPU 不断循环检查，消耗处理器周期却不做任何有生产力的事情。第二，它强制严格轮换：即使 P0 的临界区使用频率远高于 P1，也必须等对方使用后才能再次进入，高频率进程会被严重拖慢。第三，更严重的是，如果一个进程在临界区之外发生故障，另一个进程也会被永久阻塞——因为进入权已经交给了挂掉的进程，它永远不会归还。这违反了空闲让进的要求。

第二次尝试：检查对方状态
引入一个布尔数组 flag[2]，flag[i] 表示进程 Pi 是否正在临界区内。进程 P0 在进入临界区之前先检查 flag[1]，若对方不在临界区则跳出忙等循环，然后设置 flag[0] = true 并进入临界区。退出时设置 flag[0] = false。

这一方案的问题在于不能保证互斥。检查和设置操作之间不是原子的。初始状态两个 flag 均为 false，两个进程可能同时检查对方的状态，都看到对方不在临界区，于是都跳出了忙等循环，都设置了各自的 flag 并同时进入了临界区。

该问题可以用更简洁的锁变量模型来说明：一个共享变量 lock，初始值为0表示“未上锁”，1表示“已上锁”。进程先测试 lock 是否为0，若为0则将 lock 置为1并进入临界区。问题同样在于“测试”和“设置”是两条分离的操作，中间可能被打断。在单处理机系统中，中断可能发生在测试和设置之间；在多处理机系统中，两个处理器可以同时执行测试和设置。两个进程都可能看到 lock == 0，然后都将 lock 置为1，同时进入临界区。这个分析揭示了后面硬件指令方案的核心思想：如果能把测试和设置合并为一条不可分割的机器指令，就可以解决问题。

第三次尝试：先表达意愿
将 flag 的语义从“我正在临界区内”改为“我想进入临界区”。进程在检查对方之前先设置自己的 flag 为 true，然后检查对方的 flag。如果对方想进入或已经在临界区，则忙等；否则进入临界区，退出时清除自己的 flag。

这一方案的问题在于可能发生死锁。当两个进程几乎同时表达进入意愿（都设置了各自的 flag）时，它们随后互相检查，发现对方也想进入，于是双方都进入忙等循环，等待对方清除 flag。但双方都不会清除自己的 flag，因为它们都在等待对方先行动，形成了循环等待，即死锁。

第四次尝试：谦让与回退
在第三次尝试的基础上，进程设置了自己的 flag 之后，如果发现对方也想进入，就暂时清除自己的 flag，做一段随机延时，然后再次表达进入意愿。这一方案的本质是“相互谦让（mutual courtesy）”：我表达意愿，发现你也想进去，那我撤销意愿让你先进。

这一方案的问题是可能发生活锁。两个进程可能同时表达意愿，同时发现对方也想进入，于是同时撤销意愿，经过随机延时后又同时表达意愿，如此循环往复。两个进程都在不断改变自身状态，但谁都无法真正进入临界区。就像两个人在过道上迎面相遇，互相往旁边让，却总是让到同一个方向，谁也过不去。随机延时可以减少持续冲突的概率，但不能从根本上限养活锁的发生。

Dekker 的正确解决方案
为了克服第四次尝试中的相互谦让问题，算法重新引入了 turn 变量，但此时 turn 的语义不同于第一次尝试中的“轮到谁进入”。在正确方案中，flag 数组表示“我希望进入”的意愿，而 turn 仅在两个进程同时表达进入意愿时充当优先级仲裁者：turn 的值决定了在这种情况下谁优先进入。

进程 P0 的代码逻辑为：设置 flag[0] = true 表达进入意愿；然后检查 flag[1]。如果 flag[1] 为 false（对方不想进入），P0 可以直接进入临界区。如果 flag[1] 为 true（对方也想进入），则查看 turn：如果 turn == 1，表示对方优先，P0 就清除自己的 flag（flag[0] = false），在 while (turn == 1) 中忙等，等对方退出后将 turn 归还并重新表达意愿；如果 turn == 0，表示自己优先，P0 保持 flag 并等待对方清除 flag 后进入。退出临界区时，P0 将 turn 设置为1，将进入优先级交给对方，并清除自己的 flag。

这个算法同时满足了互斥、空闲让进和有限等待三个核心要求。但它仍然使用忙等机制，且代码复杂度较高，这反映了纯软件方法实现互斥的局限性。后续课程将继续介绍 Peterson 算法以及基于硬件指令和信号量的更优雅的解决方案。

并发性的广泛存在与设计困难
并发性在操作系统中无处不在，出现在三个不同的层面。第一，多个应用程序同时驻留在系统中，形成多道程序设计的并发环境。第二，结构化应用程序——一个应用可以被构建为一组并发进程，通过模块化设计让每个并发进程负责一个功能模块。第三，操作系统自身的结构——操作系统内核本身也可能被实现为一组进程或线程，它们之间也存在并发。

并发性带来的设计困难主要体现在三个方面。第一，共享全局资源充满风险：全局变量的读写次序至关重要，错误的次序可能导致信息丢失或数据一致性被破坏。第二，资源的最优分配管理非常困难：不当的分配策略可能引发死锁。第三，程序错误的定位极为困难：由于并发错误的非确定性和不可复现性，调试工作远比顺序程序复杂。
