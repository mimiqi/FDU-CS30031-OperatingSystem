读者-写者问题
读者-写者问题是进程同步领域的经典问题。系统中存在两类进程：读者进程（只对数据区域进行读操作）和写者进程（对数据区域进行写操作）。它们之间需要满足如下约束：任意数量的读者可以同时读数据区；同一时刻只能有一个写者写数据区；写者在写时，读者不能读。

这些约束的本质原因在于数据完整性：两个写者同时写入会破坏数据的完整性约束；写者正在更新数据时，数据处于不一致的中间状态，读者不应读取。

读者-写者问题与普通互斥问题的区别在于效率。若将其当作一般互斥处理，即任何时刻只允许一个进程访问数据区，则多个读者无法并行读取，这与数据区的本质属性不符，牺牲了系统性能。该问题也与生产者-消费者问题不同：在生产者-消费者模型中，生产者和消费者都既是缓冲区的读者又是写者——生产者需要读队列指针来确定写入位置，消费者也需要读指针来确定取数据的位置。因此，读者-写者问题需要专门的解决方案。

读者优先方案
第一个解决方案赋予读者优先权（Readers Have Priority），意味着写者可能发生饥饿（starvation）。

该方案引入一个整形变量 readcount，记录当前有多少个读者正在读取数据区，初始值为 0。此外引入两个信号量：信号量  用于保护共享变量 readcount 的互斥访问；信号量  用于实现写者之间以及读者群体与写者之间的互斥，初始值为 1。

单边桥问题（课堂练习）
这是一个与读者-写者问题结构类似的练习：有一座东西向的单边桥，桥上最多同时容纳 4 辆车通过。在任一时刻，桥只能允许一个方向通行：从西往东（WE）或从东往西（EW）。

解题思路：将桥视为临界资源，两组车辆（EW 群体和 WE 群体）竞争桥的通行方向。引入两个计数变量 EWcount 和 WEcount 分别统计两个方向正在通过或等待通过的车辆数，各配一个互斥信号量 EWX 和 WEX 来保护计数变量。引入信号量 bridge（初始值为 1）来控制通行方向，引入信号量 capacity（初始值为 4）来限制桥上同时通过的车辆数。

从东往西的车辆到达时：将 EWcount 加 1；若加 1 后等于 1，说明是第一辆 EW 方向的车辆，执行 wait(bridge) 竞争桥的通行方向；通过 capacity 控制桥上容量；通过桥后释放 capacity，并将 EWcount 减 1；若减 1 后为 0，执行 signal(bridge) 释放桥。从西往东的车辆对称处理即可。

管程
管程的基本概念
管程（Monitor）是由编程语言提供的互斥与同步机制，本质上是一个软件模块，包含一个或多个过程、初始化序列和局部数据。管程的主要特征包括：局部数据变量只能由管程自身的过程访问；进程通过调用管程的过程来进入管程；任何时刻只能有一个进程在管程内处于活动状态。

管程与面向对象中的对象概念相似：局部数据类似私有数据成员，过程对应方法。Java 等语言原生提供了管程机制。管程由编译器在入口点自动实现互斥机制，因此程序员不易出错——这与操作系统提供信号量类似。

管程的互斥机制
编译器在管程的每个过程入口点自动加入 wait(mutex) 操作，其中 mutex 是编译器引入的信号量（初始值为 1）。然而管程的出口并非简单的 signal(mutex)，而是加入了额外的判断逻辑。

编译器为管程额外引入了一个辅助信号量 urgent（初始值为 0）和一个整形变量 urgentcount（初始值为 0）。urgent 的作用在于：当一个进程执行 csignal 操作解除了另一个进程的阻塞后，该进程自身必须被阻塞到 urgent 上（因为管程内任何时刻只能有一个活动进程）。在过程的出口处，编译器生成的代码首先判断 urgentcount 是否大于 0：若大于 0，说明有进程在 urgent 上等待，则执行 signal(urgent) 让已进入管程的进程恢复执行；否则执行 signal(mutex) 打开管程入口，让外部进程进入。

条件变量与同步机制
条件变量（Condition Variable）是管程独有的同步机制。条件变量不是信号量，它没有值，仅是一组阻塞队列，因此不需要初始化。条件变量上有两个操作：

cwait(c)：调用进程在条件变量  上阻塞自身；
csignal(c)：恢复某个因执行 cwait(c) 而阻塞的进程。若条件变量上有多个阻塞进程，选其中一个恢复；若没有进程在等待，则什么也不做。
关键语义：当执行 csignal 的进程解除了另一个进程的阻塞后，由于管程内只能有一个活动进程，执行 csignal 的进程自身必须被阻塞，被放在 urgent 队列中等待。

用信号量实现条件变量
对于程序员定义的每一个条件变量 cond，编译器在内部引入一个信号量 condsem（初始值为 0）和一个整形计数器 condcount（初始值为 0）。信号量用于实现阻塞队列，计数器用于记录该条件变量上有多少个阻塞进程。

cwait(cond) 操作的实现：先将 condcount 加 1（因为自身即将阻塞在该条件变量上）；然后判断 urgentcount 是否大于 0——若大于 0 则执行 signal(urgent) 让 urgent 队列中的进程恢复执行，否则执行 signal(mutex) 打开管程入口；最后执行 wait(condsem) 将自身阻塞。当该进程后续被解除阻塞后，执行 condcount 减 1。

csignal(cond) 操作的实现：先将 urgentcount 加 1（因为自身即将阻塞在 urgent 上）；然后判断 condcount 是否大于 0——若大于 0 则执行 signal(condsem) 解除一个阻塞进程，然后执行 wait(urgent) 将自身阻塞；若 condcount 等于 0（没有进程在等待该条件变量），则 csignal 操作等价于什么也不做，此时 urgentcount 的加 1 与随后的减 1 相抵消。

管程的结构化理解
管程的最终结构包括：入口队列（外部进程在入口点等待进入）、条件变量队列（执行 cwait 的进程按条件变量分别排队）、以及 urgent 队列（执行 csignal 后被阻塞的进程）。一个进程进入管程后，因执行 cwait 而被放入对应条件变量的阻塞队列；另一个进程执行 csignal 解除了一个阻塞进程后，自身进入 urgent 队列；在管程出口处优先恢复 urgent 队列中的进程。

有界缓冲区生产者-消费者问题的管程实现
利用管程解决有界缓冲区（容量为 N）的生产者-消费者问题。

管程内定义了缓冲区数组 buffer[N]、写入指针 nextin、读取指针 nextout、计数器 count（当前数据项数量），以及两个条件变量 notfull 和 notempty。

生产者调用 append(char x) 过程：若 count == N（缓冲区已满），执行 cwait(notfull) 阻塞自己；否则将数据写入 buffer[nextin]，更新 nextin 和 count，执行 csignal(notempty)——因为放入了一个数据项后缓冲区一定非空，若有消费者阻塞在 notempty 上则将其唤醒。

消费者调用 take(char x) 过程：若 count == 0（缓冲区为空），执行 cwait(notempty) 阻塞；否则从 buffer[nextout] 取出数据，更新 nextout 和 count，执行 csignal(notfull) 唤醒阻塞的生产者。

该实现的逻辑清晰、可读性强：notfull 和 notempty 直观地表达了缓冲区状态的等待条件。当生产者发现缓冲区满时阻塞在 notfull 上，消费者取走一个数据项后通过 csignal(notfull) 唤醒它；对称地，消费者发现缓冲区空时阻塞在 notempty 上，生产者放入数据后通过 csignal(notempty) 唤醒它。

消息传递
消息传递（Message Passing）是操作系统提供的另一种进程间互斥与同步机制。与信号量不同，消息传递可以应用于分布式多计算机环境，因为信号量本质是共享的，无法跨机器使用。消息传递机制由操作系统以一对原语的形式提供：

send(destination, message)：向指定目的地发送一条消息；
receive(source, message)：从指定源（或任意源 ANY）接收一条消息。若没有可用消息，接收方可以阻塞等待，也可以立即返回错误码（非阻塞方式）。
同步方式
发送和接收原语均可分为阻塞式和非阻塞式。阻塞式发送（Blocking Send）意味着发送进程会被阻塞直到消息被接收方或邮箱接收；非阻塞式发送则立即返回。阻塞式接收（Blocking Receive）在无消息时阻塞等待；非阻塞式接收则立即返回空或错误码。发送方和接收方可以独立选择阻塞或非阻塞方式，形成多种组合。

直接寻址与间接寻址
直接寻址要求发送方在 send 原语中明确指出接收进程。直接寻址又分为两类：

对称直接寻址（Symmetric Direct Addressing）：发送方和接收方都必须明确指明通信对方。send(P, message) 将消息发送给进程 P，receive(Q, message) 从进程 Q 接收消息。这在 P 和 Q 之间建立了一条专用的通信链路，适用于协作者之间事先知道对方身份的场景。
非对称直接寻址（Asymmetric Direct Addressing）：只有发送方需要指明接收进程的身份，接收方通过 receive(ID, message) 接收来自任意进程的消息，ID 被设置为实际发送方的身份。这种模式适用于客户端-服务器架构：服务器（如打印机服务器）接收来自任意客户端的请求，但通过 ID 知道请求的来源。
间接寻址则不将消息直接发送给进程，而是发送给一个共享的数据结构——邮箱（Mailbox）。发送方将消息放入邮箱，接收方从邮箱取消息。每个邮箱有唯一的标识符。间接寻址的优点是灵活性更高，可以支持四种通信模式：

一对一：一个发送进程和一个接收进程，建立私有链路；
多对一：多个发送进程向一个邮箱发消息，一个接收进程取消息，对应客户端-服务器模型；
一对多：一个发送进程向邮箱发消息，多个接收进程取消息，可用于广播场景；
多对多：多个发送进程和多个接收进程共享邮箱，对应多服务器并发服务的场景（如负载均衡）。
邮箱的所有权有两种模式：一是邮箱归属于某个进程（该进程创建并拥有邮箱，只有所有者进程可以接收消息，其他进程只能发送）；二是邮箱归属于系统（独立存在，不附加于任何进程，其他进程可动态连接到邮箱）。

消息缓冲
无论直接寻址还是间接寻址，消息交换都需要一个消息队列。队列的容量有三种实现方式：

零容量（Zero Capacity）：队列长度为 0，发送方必须阻塞直到接收方接收该消息；
有界容量（Bounded Capacity）：队列具有有限长度 n，当队列满时发送方必须阻塞；
无界容量（Unbounded Capacity）：队列长度潜在无限，发送方永远不会阻塞。
消息的发送方实际上是消息的生产者，接收方是消息的消费者，因此消息传递本质上是一个生产者-消费者问题，可以通过有界缓冲区机制来实现。

用消息传递实现互斥
使用消息传递实现互斥的方法很简洁：主函数创建一个邮箱 ，向其中发送一条空消息，然后启动 N 个并发进程。每个进程试图从邮箱  中接收消息；一旦成功接收到那条唯一的消息，就可以进入临界区；执行完临界区后将消息发回邮箱。由于只有一条消息，任何时刻只有一个进程能获得它，从而实现了互斥。

有界缓冲区生产者-消费者问题也可以通过消息传递实现：主函数创建两个邮箱 mayproduce 和 mayconsume。初始时向 mayproduce 发送 capacity 条空消息（表示可以生产 capacity 个数据项）。生产者每次从 mayproduce 接收一条消息（消耗一个“生产额度”），生产后将产品消息发送到 mayconsume；消费者从 mayconsume 接收消息，消费后向 mayproduce 发回一条空消息（释放一个生产额度）。这种对称的设计自然地实现了缓冲区容量的控制。

死锁
死锁的定义
死锁（Deadlock）指的是一组进程中的每个进程都在等待一个事件，而该事件只能由这组进程中的其他进程引起。这意味着所有进程都处于永久阻塞状态。如果一个进程等待的事件可以由这组进程之外的进程引起（如另一个仍在运行的进程），则不属于死锁。死锁不存在一个有效的通用解决方案。

一个直观的生活类比例子是交叉路口的死锁：四辆车各占据一个方向的车道，每辆车都只能直行、不能后退或拐弯，每辆车都在等待另一辆车做出动作，而那个动作又依赖于其他车辆，形成了循环等待。

联合进程图
联合进程图（Joint Progress Diagram）用于刻画两个进程共享两个临界资源时的执行轨迹。横轴表示进程 P 的执行进度，纵轴表示进程 Q 的执行进度。以两个资源和两个进程为例：进程 P 依次获取 A、获取 B、释放 A、释放 B；进程 Q 依次获取 B、获取 A、释放 B、释放 A。

图中每条资源获取线（Get A、Get B）和相应的释放线（Release A、Release B）之间形成了一个区域，表示该资源被某个进程持有。当两条 Get 线之间的区域同时覆盖了 P 和 Q 的资源持有区间时，形成了阴影区域——该区域表示资源 A 和 B 分别被 P 和 Q 同时持有。

在联合进程图中，阴影区域是禁止进入的，因为进入该区域意味着违背了临界资源的互斥约束。例如，若轨迹穿过“Get A(P)”这条线，说明进程 P 获得了 A；此时若轨迹再试图穿“Get A(Q)”这条线，由于信号量 A 已被 P 持有（值为 0），Q 执行 wait 操作将被阻塞，因此轨迹无法穿过。

关键的灰色区域被称为“必然死锁区”：一旦执行轨迹进入该区域（即 P 持有 A、Q 持有 B），由于 P 下一步要获取 B（已被 Q 持有）、Q 下一步要获取 A（已被 P 持有），两条轨迹都无法继续前进，必然发生死锁。从死锁定义来看，每个进程都在等待对方释放资源，形成了不可解开的循环等待。

换一种资源请求顺序就不会发生死锁：如果进程 P 改为获取 A 后立即释放 A，再去获取 B 后立即释放 B，而 Q 仍然是获取 B 后释放 B、再获取 A 后释放 A，则联合进程图中虽然仍存在禁止进入的互斥区域，但不存在“必然死锁区”——任何执行轨迹都能找到一条走出图的路径。这一对比说明了死锁的形成依赖于进程的资源请求顺序，也为后面讲银行家算法时理解其保守性做铺垫。

可重用资源与可消费资源
可重用资源（Reusable Resource）指一次只能被一个进程安全使用、但使用不会销毁该资源的资源。典型的可重用资源包括处理器、打印机、内存等硬件设备，也包括某些数据结构。进程对可重用资源的使用遵循固定的顺序：请求（Request/Get）→ 使用（Use）→ 释放（Release）。若请求不能立即得到满足，请求进程必须等待。这种请求-释放机制本质上对应信号量的 wait 和 signal 操作，操作系统通过系统调用来实现。

可重用资源的死锁示例：进程 P 先请求资源 D 再请求资源 T，使用后释放；进程 Q 先请求 T 再请求 D。若 P 先获得 D、Q 先获得 T，则 P 请求 T 时被阻塞（T 在 Q 手中），Q 请求 D 时被阻塞（D 在 P 手中），两个进程死锁。另一个内存分配的例子：系统有 200KB 可用空间，P1 先请求 80KB（获得分配），P2 请求 70KB（获得分配，剩余 50KB）；随后 P1 请求 60KB（被阻塞），P2 请求 80KB（被阻塞），两者形成死锁。

可消费资源（Consumable Resource）指可以被创建（生产）和销毁（消费）的资源，如消息传递中的消息。发送进程创建消息，接收进程消费消息。可消费资源的死锁示例：P1 要通过对称直接寻址从 P2 接收消息后才向 P2 发送消息，P2 也做同样的约定，则两个进程互相等待对方发送消息，形成死锁。

本课程的限定：死锁部分仅关注可重用资源，不研究可消费资源。

死锁的四个必要条件
在只考虑可重用资源的前提下，死锁发生必须同时满足以下四个必要条件：

第一个必要条件是互斥（Mutual Exclusion）。资源必须是一类资源（临界资源），一次只能被一个进程使用。如果资源可以同时被多个进程使用，就不会因竞争而发生死锁。这是从资源节点的角度。

第二个必要条件是占有且等待（Hold-and-Wait）。进程必须已经持有至少一个资源，同时又在等待获取其他资源。如果进程不持有任何资源，或者持有资源后不再请求新的资源，就不会死锁。这是从进程节点的角度。

第三个必要条件是非抢占（No Preemption）。已经分配给进程的资源不能被强制收回。资源只能由持有它的进程自愿释放。这是从资源-进程的分配边角度。

第四个必要条件是循环等待（Circular Wait）。系统中必须存在一个进程的闭环，每个进程持有至少一个资源，并且正在等待闭环中下一个进程所持有的资源。这是从整个系统全局的角度。

这四个条件可以借助资源分配图来记忆：图中有两类节点——进程节点 P 和资源节点 R；有两种有向边——资源到进程的分配边（Assignment Edge）和进程到资源的请求边（Request Edge）。从节点角度看，资源节点对应互斥条件，进程节点对应占有且等待条件；从分配边的角度看，对应非抢占条件；从整个图的角度看，存在一个闭合的循环链就对应循环等待条件。这四个条件并非完全独立：循环等待条件实际上蕴含了占有且等待条件。

资源分配图
资源分配图（Resource Allocation Graph）是刻画系统资源分配状态的形式化工具。图中的顶点集  分为两个子集：进程节点集  和资源类型集 。边集  包含两种有向边：请求边 （进程  请求资源  的一个实例）和分配边 （资源  的一个实例分配给了进程 ）。

在图形表示中，每个进程用圆圈表示，每类资源用方块表示，方块内的小圆点表示该类资源的实例数量。例如，若  有两个实例（如两台打印机），方块内就有两个小圆点。

通过资源分配图判断死锁：如果 P1 请求 R1（但没有分配边指向 R1），R1 分配给 P2，同时 P2 请求 R3 且 R3 分配给 P3，此时 P1 和 P2 都处于阻塞状态，但系统没有死锁。从死锁定义出发：P1 等待的事件（R1 的释放）只能由 P2 引起，P2 等待的事件（R3 的释放）由 P3 引起，而 P3 不在这个集合中；从必要条件出发，图中不存在闭合的循环链。因此，仅仅有进程阻塞并不意味着系统死锁，关键在于是否存在由这组进程自身构成的封闭等待环。
