进程描述符与进程控制
在操作系统内核中，进程描述符（Process Descriptor），也常被称为进程控制块（Process Control Block, PCB），是操作系统管理进程的核心数据结构。当系统创建一个新的进程时，它必须为其分配一组独立且完整的信息空间，这组空间就是PCB。由于操作系统需要同时管理多个并发进程，它会将系统中所有进程的PCB组织在一起，形成一个被称为进程表的数据结构。每个进程在进程表中对应一个条目，即它的PCB。每个进程拥有一个在系统内全局唯一的标识符，称为进程ID（PID）。通过PID，操作系统就能在进程表中找到对应的PCB，进而获取该进程的全部关键信息，并对其实施控制和管理。因此，PCB成为了操作系统感知和管理进程的唯一依据，它将抽象的进程实体化，是操作系统内核运作的基石。

PCB中存储的信息通常被组织为三大类别，它们共同构成了一个进程的完整画像。

进程标识信息
这部分最为直观，主要包含进程ID（PID），用来在系统范围内唯一标识该进程。此外，还包含父进程ID（PPID），它标识了创建该进程的父进程，由此可以构建起系统内所有进程的树状父子关系结构。同时，还有用户ID（UID）和组ID（GID），它们定义了进程的归属以及访问系统资源的权限边界。

处理器状态信息
这部分信息是CPU虚拟化的基石，它的核心作用是保存和恢复CPU的执行现场。在多道程序环境下，一个进程不会一直占用CPU。当它被中断，比如时间片用完时，操作系统必须能够保存它当前在CPU上的所有寄存器状态（如程序计数器PC、通用寄存器、状态寄存器等）到其PCB中。之后，当这个进程再次被调度获得CPU时，操作系统会从其PCB中恢复这些状态，使进程能够从上次被中断的断点处无缝地继续执行。正是通过这种PCB中保存的CPU状态快照，单一的物理CPU才被虚拟化为多个逻辑上的CPU，实现了进程的并发执行。

进程控制信息
这是一个庞大且繁杂的信息类别，包含了除前两类外，操作系统对该进程进行管理与控制所需的所有其他信息。它的内容包括：
- 调度和状态信息：记录了进程当前所处的状态（运行、就绪、阻塞等）。调度优先级是关键，优先级越高的进程越会被优先调度。此外，还包含一些与具体调度算法相关的信息，例如进程在就绪队列中已等待的时长，或它上一次获得CPU后执行了多久。
- 事件标识：当一个进程处于阻塞态时，这里会记录它在等待哪个具体事件的发生。
- 数据结构化信息：操作系统需要将处于相同状态的进程PCB以某种方式组织起来，比如形成就绪队列、阻塞队列等。这些PCB之间会通过指针链接。同时，进程间的父子关系也通过类似的方式形成树状结构。
- 内存管理信息：记录了该进程的虚拟地址空间是如何映射到物理内存的。其具体的数据结构取决于操作系统所采用的内存管理方案。如果采用简单的连续内存分配，那么PCB可能只需要记录进程在物理内存中的起始地址  和长度 ，表明它占用了物理地址  的区域。如果采用分页或分段等非连续分配方案，则PCB会包含指向页表或段表的指针，这些表格记录了该进程的每一个页面或段在物理内存中的具体位置。
- 资源拥有情况：通过一个文件描述符表指针，记录了该进程打开的所有文件。一个进程在创建时，默认会打开三个标准文件：标准输入（通常是键盘）、标准输出和标准错误（通常是显示终端）。
- 记账信息：记录了进程对处理器和其他资源的使用历史，可用于系统计费和性能分析。

进程控制
进程作为一个动态实体，有其从创建到终止的完整生命周期，操作系统通过一系列的进程控制操作来管理这一过程。

进程创建
一个静态程序被转换为动态进程，是一个复杂的步骤序列。首先，需要将存储在磁盘上的可执行文件中的代码段和静态数据段加载到内存（即进程的地址空间）中。接着，操作系统要为该进程的动态内存区域分配空间，这包括两部分：一个是栈，它用于存放函数调用时的局部变量、函数参数及返回地址，是随着函数调用的深入而隐式自动分配的；另一个是堆，它用于支持显式请求的动态内存分配，如C语言中的 malloc()。还需执行一系列的I/O相关初始化，例如在类Unix系统中，创建进程时会默认打开标准输入、输出和错误这三个文件描述符。最后，程序会从其入口点开始执行。

在Unix或Linux系统中，进程的创建通过 fork() 系统调用来完成。fork() 会创建一个与父进程几乎完全相同的子进程副本。它们的区别在于 fork() 的返回值：对父进程，fork() 返回大于0的子进程PID；对子进程，fork() 返回0。程序通过检查返回值来执行不同的代码分支。通常，父进程会调用 wait() 系统调用，让自己进入阻塞状态，等待子进程的终止，以实现同步。

Unix设计的一个重要特点是将 fork() 和 exec() 两个系统调用分离。在Windows中，创建新进程并指定其执行的程序通常一步完成。但在Unix中，fork() 仅创建一个当前进程的副本，而 exec() 系列系统调用则用于用一个新的程序映像替换当前进程的地址空间。这种分离为Shell程序的强大功能提供了基础，允许Shell在 fork() 之后、exec() 之前做一些额外工作。一个典型例子是输出重定向：当执行 wc p3.c > newfile.txt 时，Shell首先 fork() 出一个子进程，然后在子进程中关闭其标准输出文件描述符，并代以打开文件 newfile.txt，最后再 exec() 执行 wc 程序。这样，wc 向标准输出的所有内容就会被重定向到文件中。另一个例子是管道机制：当执行 grep -o foo file | wc -l 时，Shell会调用 pipe() 系统调用创建一个内核管道，然后分别创建两个子进程，将一个进程的标准输出连接到管道的写入端，将另一个进程的标准输入连接到管道的读出端，从而实现两个进程间的数据流传递。

进程终止
当一个进程执行完最后一条语句，它会调用 exit() 系统调用来请求操作系统将其删除。此时，操作系统会回收分配给该进程的所有资源，包括物理和虚拟内存、打开的文件以及I/O缓冲区等。进程在终止时，可以通过 exit() 传递一个状态值，而它正在等待的父进程则通过 wait() 获取该状态值，从而了解子进程的退出原因。

执行模式与模式切换
为了保证操作系统的安全性和稳定性，现代CPU至少支持两种执行模式，即用户态和内核态，它们代表了不同的特权级别。

内核态：拥有对硬件和内存的最高访问权限。CPU在此模式下可以执行所有指令，包括特权指令，并能访问所有内存区域。操作系统的内核代码就在此模式下运行，是受信任的代码。
用户态：特权级别较低。普通应用程序在此模式下运行，不能执行特权指令，也不能直接访问受保护的内核内存区域。这确保了用户程序的错误或恶意行为不会破坏整个系统。
系统启动时，CPU处于内核态，用于加载和初始化操作系统。在准备运行用户应用程序之前，操作系统会将CPU切换到用户态。应用程序自身无法主动将CPU切换回内核态，因为修改处理器状态寄存器的指令本身是特权指令。重新进入内核态的途径是严格受控的，只有以下三类事件能够触发模式切换：

触发模式切换的三类事件
系统调用：用户程序主动请求操作系统服务（如读写文件、创建进程）时，会执行一条特定的机器指令。这条指令会产生一次软中断，迫使CPU从用户态切换到内核态，然后跳转到操作系统的相应服务代码去执行。
陷阱：这是由当前正在运行的指令自身产生的一种同步异常或错误。例如，除零错误（divide-by-zero）、访问非法内存地址或在用户态下试图执行特权指令。当CPU检测到这些情况时，会强制切换到内核态，让操作系统来处理这个错误。
硬件中断：这是由外部硬件设备（如时钟、键盘、磁盘）产生的异步事件，它独立于当前运行的进程。它通过信号线通知CPU，打断当前进程的执行，迫使CPU进入内核态来处理这个外部事件。
模式切换的工作流程
模式切换并不改变当前正在运行的进程或线程，它仅仅是在用户态和内核态之间进行切换，其核心步骤通常为五步：
1. 保护现场：CPU自动将用户态的关键寄存器（如程序计数器EIP、栈指针ESP等）压入该进程的内核栈，这部分需要保存的寄存器内容远少于完整的上下文切换。
2. 权限升级：CPU的特权级从用户态切换至内核态，从而获得执行内核代码、访问所有内存的权限。
3. 内核执行：CPU跳转到与事件（系统调用号、中断号）对应的内核处理程序入口，执行具体的操作系统功能代码。
4. 恢复现场：内核代码执行完毕后，从内核栈中弹出之前保存的用户态寄存器值，恢复程序执行前的环境。
5. 权限回落：CPU的特权级从内核态切换回用户态，程序从被中断的断点处继续执行。

由于模式切换不改变当前进程，地址空间保持不变，因此其开销是相对较低的。

上下文切换与进程切换
上下文切换是多道程序操作系统最核心的特性之一，它允许多个进程或线程共享单个CPU。一个完整的进程上下文切换，意味着操作系统将CPU的控制权从一个正在运行的进程移交给另一个进程。

进程切换的触发与步骤
进程切换一定会触发模式切换，但模式切换不一定会导致进程切换。例如，当发生一次时钟中断时，内核的调度程序判定当前进程的时间片已用完，就会决定进行一次进程切换。而发生一次磁盘I/O完成的中断时，可能只是将一个等待该I/O的阻塞进程变为就绪状态并放入就绪队列，如果它的优先级没有高到可以抢占当前进程，就不会发生进程切换。进程切换的主要步骤包括：
1. 保存上下文：保存当前运行进程的完整CPU状态（所有寄存器、程序计数器等）到其PCB中。
2. 更新PCB：将当前进程的状态（从运行态）修改为就绪态或阻塞态，并将其PCB移动到相应的队列。
3. 选择新进程：根据调度算法，从就绪队列中选择一个新的进程来执行。
4. 更新新进程PCB：将选中的新进程的状态修改为运行态。
5. 更新内存管理数据结构：这是开销最大的步骤之一。操作系统需要切换到新进程的地址空间，这可能意味着更新页表基址寄存器等，以便MMU使用新进程的页表进行地址转换。
6. 恢复上下文：从新进程的PCB中恢复其之前保存的CPU状态，CPU即开始执行新进程的代码。

与其说进程切换本身的操作耗时，不如说其最大的开销来自于间接的惩罚。由于地址空间发生了改变，以前缓存在TLB中的地址转换条目和CPU高速缓存中的大部分与旧进程相关的数据都会瞬间失效。新进程开始执行时，会发生大量的TLB缺失和缓存未命中，需要重新访问内存来填充，这导致了显著的性能下降。这正是模式切换（不改变地址空间）的开销显著低于进程切换的根本原因。

线程概念与多线程模型
经典的进程模型将进程视为资源拥有单元和调度执行单元的统一体。每个传统进程只有一个控制线程，即串行地执行一条指令流。而多线程的引入，正是为了将这两个概念分离开。

进程与线程的分离
在多线程环境下，进程成为了拥有资源（地址空间、打开的文件、信号等）的单元和提供保护的单元。而线程则成为了CPU调度和分派的基本单位。一个进程内部可以包含多个线程，这些线程共享该进程的整个地址空间和所有资源，但每个线程都拥有自己独立的、不可或缺的执行上下文，这包括：
- 线程ID：在线程所属的进程内唯一的标识符。
- 程序计数器：指向当前正在执行或下一条将要执行的指令地址。
- 一组寄存器：保存该线程当前的CPU运算状态。
- 一个独立的栈：每个线程都有自己独立的函数调用链和历史，因此需要独立的栈空间来保存各自的局部变量、函数参数和返回地址。

正是因为同一个进程内的多个线程共享同一个地址空间，它们之间的通信变得异常简单和高效，因为它们可以直接通过读写全局变量或向共享内存区域写入数据来进行交互，无需经过开销昂贵的内核。

上下文切换的类型比较
引入线程后，上下文切换被细分为两类，其开销存在巨大差异：
- 线程切换：发生在同一个进程内的两个线程之间。由于共享地址空间，切换时只需保存和恢复CPU寄存器、程序计数器和栈指针，完全不需要更新内存管理数据结构。因此，TLB和缓存依然有效，切换开销非常低。
- 进程切换：发生在不同进程的线程之间。它需要执行完整的切换流程，特别是更新内存管理结构，导致地址空间切换，这会带来TLB刷新和缓存失效的严重惩罚，切换开销很高。

多线程编程的动机与优势
一个典型的多线程应用场景是执行两个远程过程调用。在单线程程序中，需要依次发起请求、等待返回、再发起下一个请求，两个等待时间是串行的。而在多线程程序中，可以为每个RPC分配一个独立线程，它们可以并发地发起请求并交叉等待，实现I/O操作的重叠，从而显著加速程序。与使用多进程实现同样的并发效果相比，多线程具有以下优势：
1. 响应性：在交互式应用中，可以将处理用户界面的线程与执行耗时计算或阻塞I/O操作的线程分开，确保用户界面始终能快速响应用户操作。
2. 资源共享：线程间默认共享进程的内存和资源，通信极其方便。
3. 经济性：创建和终止线程的速度远快于进程；同一进程内线程切换的开销远低于进程切换；线程间通信无需调用内核，效率更高。
4. 可扩展性：在多处理器系统上，可以将同一进程的多个线程映射到不同的处理器核上，实现真正的并行执行，从而充分利用硬件性能。

用户级线程与内核级线程
多线程的实现方式主要有两种：用户级线程和内核级线程。

用户级线程
在纯ULT模型中，所有的线程管理工作都由一个运行在用户空间的线程库来完成。线程库提供了创建、销毁、调度、同步线程以及保存和恢复线程上下文的全部功能。对于操作系统内核而言，它完全感知不到线程的存在，它依然只看到一个单线程的进程。内核的调度对象是进程，而非线程。

ULT在用户空间为每个进程维护一个线程表，跟踪该进程内部的所有线程及其状态（运行、就绪、阻塞）。这就产生了两级状态：进程状态和线程状态。其关系可以通过三种场景来理解，假设进程B内有线程1和线程2，初始状态下线程2在CPU上运行，因此进程B为运行态，线程2为运行态，线程1为就绪态：
1. 线程2执行阻塞式系统调用：系统调用导致进程B被内核阻塞，进程B变为阻塞态。尽管从逻辑上线程1本可以运行，但由于进程B整体失去了CPU，线程1也会无法执行，保持着就绪态。这暴露了ULT的一个关键缺陷：一个线程的阻塞会导致整个进程内所有线程都无法运行。
2. 发生时钟中断且时间片用完：内核将进程B的运行态改为就绪态，并将其放回就绪队列。进程B内部，线程2和线程1的状态保持不变，但任何线程都无法获得CPU时间，直到进程B下次被调度运行。当它再次运行时，线程库会恢复线程2继续执行。
3. 线程2主动等待线程1完成某项工作：这属于进程内部的同步。线程2调用线程库函数进入阻塞态，线程库则选择就绪的线程1投入运行。整个过程都发生在用户空间，不涉及内核，进程B整体始终处于运行态。

用户级线程的优缺点十分鲜明。其优点是：线程切换无需陷入内核，速度快；调度策略可由应用程序专用，灵活性强；可以在任何不支持线程的操作系统上运行。其缺点是：一个线程的阻塞式系统调用或缺页异常会阻塞整个进程，因为内核无法感知到进程中还有其他可运行的线程；无法在多处理器系统上实现并行，因为内核一次只会将一个进程分配给一个CPU。

为解决阻塞问题，一种技术是使用Jacket（外套）技术。其思想是在系统调用外包裹一层同名的库函数。当一个线程调用IO库函数时，代码会先检查IO设备是否忙。如果忙，则不发起系统调用，而是由线程库将该线程置为就绪态并切换到另一个线程；只有当检查到设备就绪时，才真正发起可能阻塞的系统调用。这在一定程度上缓解了问题，但无法根治。

内核级线程
在纯KLT模型中，所有线程的创建、调度和管理工作全部由操作系统内核完成。内核既维护进程表，也维护一个全局的线程表，来跟踪系统中的所有线程。应用程序无需包含线程管理代码，只需使用内核提供的线程API。

KLT的优点恰好弥补了ULT的缺陷：内核可以将同一个进程的多个线程同时调度到多个处理器上，实现真正的并行；当进程内的一个线程因系统调用而阻塞时，内核可以立即调度同一个进程内的另一个就绪线程去执行，而不会阻塞整个进程；内核自身的代码也可以被设计为多线程的，从而提高操作系统本身的并发能力。其缺点则在于：由于所有线程操作都涉及系统调用，引发了开销较大的模式切换；即使是在同一进程内两个线程间简单的控制权移交，也必须经过内核，效率相较于ULT的纯用户态切换要低。

线程的实现模型
在实际系统中，会将用户级线程和内核级线程结合起来，形成不同的对应关系：
- 多对一模型：多个用户级线程映射到单个内核级线程。这实质上是纯ULT的实现，一个用户线程阻塞会导致所有线程阻塞，且无法利用多处理器。
- 一对一模型：每个用户级线程都映射到一个独立的内核级线程。这实质上是纯KLT的实现，解决了阻塞和并行问题，但创建用户线程的开销较大，系统需限制线程总数。
- 多对多模型：将多个用户级线程多路复用到数量较少或相等的内核级线程上。这是一种折中方案，内核线程池作为“虚拟处理器”提供给用户态的线程调度器。这既能像KLT那样实现并发和并行，又能通过复用减少内核线程的创建数量，并且通过将需要频繁同步的线程映射到同一个内核线程上，既可以回避部分内核切换开销，又实现了极大的灵活性。
