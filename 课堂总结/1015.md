Peterson 算法
算法背景与设计思想
在上一节课中，我们已经系统回顾了 Dekker 算法的四次尝试：第一次严格交替因性能缺陷被否定；第二次不能保证互斥；第三次可能发生死锁；第四次虽然通过"撤回意愿"避免了死锁，却又引入了活锁的可能性。Dekker 算法最终虽然正确，但其逻辑相当复杂，理解门槛较高。Patrick Peterson 于 1981 年提出的算法在功能上与 Dekker 算法等价，但代码结构更为简洁优雅。其核心思想是：当一个进程位于临界区内时，能够阻止另一个进程进入临界区。

软件方法的局限
包括 Peterson 算法在内的所有软件方法，都把互斥的责任完全交给了程序员。这意味着实现过程极易出错，而且不可避免地存在忙碌等待问题——等待进程在 while 循环中反复测试条件，浪费 CPU 时间周期。

硬件支持：关中断
机制原理与适用范围
硬件支持是实现互斥的第二类方法。其中第一种是关中断。在单处理机系统中，并发进程只能交替执行，无法真正并行。一个进程开始运行后，只有在三种情况下操作系统才能获得控制权：进程显式地调用系统调用；硬件中断发生（如定时器到期或磁盘 I/O 完成）；以及当前执行的指令引发异常（如除零错误、特权指令违规或访问非法内存地址）。

因此，如果一个进程在进入临界区之前关闭中断，且其在临界区内既不发生异常、也不主动调用系统调用，那么它就不会被硬件中断打断，进程切换就不会发生，从而保证了互斥。退出临界区时，进程重新打开中断。

局限性与安全性问题
关中断方法对多处理机系统不适用。因为关闭中断只能作用于当前进程所在的 CPU，无法阻止其他 CPU 上的进程并行执行并访问同一临界区。

更为严重的是，将关中断的能力交给用户进程是不当的。若用户进程关闭中断后执行一个空的 while 死循环，内部既不会产生异常，也没有系统调用，那么操作系统将永远无法重新获得控制权，整个系统将崩溃。因此，关中断只能由操作系统内核自身在严格测试的前提下使用，不能作为用户可用的同步原语。

硬件支持：Test and Set 指令
问题的根源
在 Dekker 算法的第二次尝试中，我们看到了"先测试锁变量、再将锁变量设置为锁定值"的逻辑缺陷：两个进程可能先后观察到锁是打开的，然后同时进入临界区。核心问题在于测试和设置这两个操作之间可能发生交替执行，二者没有被原子化。

TSL 指令的原子性保证
为了从根本上解决这一问题，某些面向多处理机设计的计算机提供了一条特殊的机器指令 TSL（Test and Set Lock）。其汇编形式为 TSL RX, lock，功能是：将内存字 lock 的内容读入寄存器 RX，然后向内存地址 lock 存储一个非零值。关键在于，读取和存储这两个操作在单个指令周期内不可分割地完成。执行 TSL 指令的 CPU 会锁定内存总线，禁止其他 CPU 在指令完成之前访问内存，从而在硬件层面保证了原子性。

硬件支持：Exchange 指令
交换指令的原子语义
另一种常见的同步指令是 Exchange（在 Intel x86 架构上称为 XCHG）。该指令原子地交换两个位置的内容，例如一个寄存器和一个内存字的值。其逻辑实现可表示为：

void exchange(int *register, int *memory) {
    int temp;
    temp = *memory;
    *memory = *register;
    *register = temp;
}

机器指令方法的优缺点
机器指令方法的优点在于：适用于任意数量的进程，无论是单处理机还是共享内存的多处理机系统；实现简单，便于验证正确性；可以为多个不同的临界区分别设置一个锁变量。

缺点同样明显。首先，存在忙碌等待，等待进程在循环中反复执行 test-and-set 或 exchange，浪费处理器时间。其次，可能发生饥饿：当多个进程等待同一临界区时，选择哪个进程进入是随机的，某个运气差的进程可能无限期得不到访问权。第三，可能发生死锁，其典型原因是优先级倒置：假设低优先级进程  正在临界区内执行，此时高优先级进程  进入就绪队列并抢占 CPU，然后尝试进入同一临界区。由于临界区被  占用， 在忙碌等待循环中消耗 CPU；而  因优先级低而无法获得 CPU 释放临界区，形成了  等待 CPU、 等待临界区的互相等待局面。解决方案之一是优先级继承协议。

信号量的定义
信号量作为抽象数据类型
信号量是操作系统提供的一种同步机制，本质上是一个抽象数据类型。一个计数信号量包含一个整数值和一个阻塞进程队列。在信号量上，只有三种操作被允许：初始化（initialize）、wait 操作（也称为 P 操作或 down 操作）和 signal 操作（也称为 V 操作或 up 操作）。尽管信号量内部有一个整数值，但从面向对象的角度来看，用户不能对该值做任何其他操作。

wait 与 signal 的语义
wait 操作将信号量的计数值递减 。如果递减后的值小于 ，则执行该操作的进程被放入信号量的阻塞队列中并被阻塞。signal 操作将信号量的计数值递增 。如果递增后的值小于等于 ，则从队列中移除一个进程并将其放入就绪队列。

伪代码实现如下：

void wait(semaphore s) {
    s.count--;
    if (s.count < 0) {
        place this process in s.queue;
        block this process;
    }
}

void signal(semaphore s) {
    s.count++;
    if (s.count <= 0) {
        remove a process P from s.queue;
        place process P on ready list;
    }
}
注意这里的细节：wait 使用严格小于号（），signal 使用小于等于号（）。这是因为 wait 递减之后，若结果为负数，其绝对值恰好表示等待进程的数量；而 signal 递增之后，若结果仍为负数或零，说明递减前存在等待进程，需要唤醒一个。

信号量的实现
信号量自身的原子性
信号量虽然是同步机制，但其自身必须作为一个临界资源来保护。wait 和 signal 必须实现为原子原语。在单处理机上，可以通过关中断来实现：在执行 wait 或 signal 主体代码期间关闭中断，执行完毕后再打开。由于 wait 和 signal 只包含十几条机器指令，关中断的时间极短，这在单处理机上是合理的。

伪代码：

void wait(s) {
    inhibit interrupts;
    s.count--;
    if (s.count < 0) {
        place this process in s.queue;
        block this process;
        allow interrupts;
    } else {
        allow interrupts;
    }
}
使用 test-and-set 实现信号量
在多处理机上，可以通过 test-and-set 指令保护信号量。为每个信号量增加一个整型变量 s.flag 作为锁：

void wait(s) {
    while (testset(s.flag)) /* do nothing */;
    s.count--;
    if (s.count < 0) {
        place this process in s.queue;
        block this process;
        s.flag = 0;
    } else {
        s.flag = 0;
    }
}
为什么信号量优于纯忙碌等待
表面上看，用 test-and-set 实现信号量似乎并没有消除忙碌等待。关键在于忙碌等待的粒度发生了根本性的转化。test-and-set 保护的锁变量本身的空间和时间开销极小，wait 和 signal 操作只有约十几条指令，很快就能释放锁。即使发生竞争，等待的 CPU 周期数也非常少。

相比之下，如果用 test-and-set 直接保护一个"大"的临界区（如打印机访问），等待进程可能需要在循环中消耗大量 CPU 时间。而信号量的优势在于：当进程发现大临界区已被占用时，它会被阻塞而不是继续忙碌等待，从而让出 CPU。因此，信号量的本质是将大粒度的忙碌等待转换为小粒度的短暂等待，大幅度减少了 CPU 周期的浪费。

理发店问题
场景描述
一个理发店中有三张理发椅、三个理发师、一张可坐四人的沙发，以及一个可供站立的等待区域。理发店最多容纳  位顾客。此外还有一个收银台，理发师需要轮流充当收银员——三个理发师和一个收银任务共四个角色，但同一时刻最多只有三个在执行（因为总共只有三个人）。

顾客的行为流程为：等待进入理发店  进入店后等待坐沙发  从沙发起来坐到理发椅上  理发师理发  去收银台付款并拿收据  离开理发店。

公平性问题与改进
上述基本方案存在一个公平性问题：当三个顾客同时坐在理发椅上时，理发师无法知道自己在给哪一位顾客理发。三个理发师完成理发后都会执行 ，但信号量是一个队列，唤醒的顾客按照等待顺序而不是实际完成顺序确定。如果第三位顾客理发很快，而第一位顾客需要复杂发型，第三位顾客可能会被迫等到第一位顾客完成后才能离开理发椅。

改进方案的核心思想是引入顾客编号。系统维护一个全局计数器 count，每个顾客进入店时在互斥保护下递增 count 并获得唯一的编号 custnr。顾客坐上理发椅后将自己的编号入队。理发师被唤醒后从队列中取出编号，从而知道自己服务的顾客是谁。理发完成后，理发师通过 finished[b_cust] 这个信号量数组精确唤醒对应的顾客。这样就保证了理发椅的释放是按实际完成顺序进行的。

读者—写者问题概述
问题的定义
读者—写者问题是另一个经典的同步问题。系统中有多个进程，其中读者进程只对数据区进行读操作，写者进程只对数据区进行写操作。约束条件为：任意数量的读者可以同时读取数据区；写者之间必须互斥；读者和写者之间也必须互斥。

为什么互斥方案不够好
若简单地为所有读者和写者设置同一个互斥信号量，虽然正确性没有问题，但效率极低。因为多个读者同时阅读并不会破坏数据一致性，如果强制读者之间互斥，就白白降低了系统的并发度。读者—写者问题的目标就是设计一个方案，在保持读者与写者互斥、写者与写者互斥的前提下，允许多个读者并发地进入数据区。

与生产者—消费者问题的区别
读者—写者问题与生产者—消费者问题的根本不同在于：生产者和消费者都既是"读者"又是"写者"。生产者放入产品前需要读取  指针和缓冲区状态，放入产品时又进行写操作；消费者取产品前需要读取  指针，取出后修改  也是写操作。因此生产者—消费者问题中，所有进程对共享数据的访问方式相同，必须完全互斥。而读者—写者问题中，读者的操作是只读的，可以被并发执行；只有写者的操作才需要排他性的互斥。这个差异化导致读者—写者问题的解决方案要比生产者—消费者问题复杂一些，将在下一节课中详细讨论。
